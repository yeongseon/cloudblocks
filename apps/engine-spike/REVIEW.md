# Rendering study evidence — issue #1927

## User visual preference

After viewing the local candidates, the user said **Lit 3D looks better**. Treat Lit 3D as the preferred visual direction for the next, timeboxed interaction spike; keep production SVG as the baseline and potential WebGL fallback. This is a subjective preference, not a measured pass for editor behavior, accessibility, or performance and not a decision to migrate the production renderer.

## Rejected mid-body connection experiment

The user supplied a separate image of hoses plugged into the middle of blocks. A temporary Lit 3D comparison rendered all five connections as ribbed mid-height cables. Visual review found a dense, unpleasant cluster: crossing hoses obscured blocks, labels, and connection direction. The user rejected this appearance. The cable geometry, toggle, and active capture were removed; `?mode=three` displays surface rails again. The reference image was not copied into the repository.

**Next visual question:** preserve surface-first routing and the universal port glyph, but determine how a complete connection remains visible across stacked containers. Long routes should stay thin and typed. Do not reintroduce free-floating hoses or claim production routing parity. No alternative has been approved for production.

The riser sketch showed a connector at **every** endpoint, which the user found awkward when overlapping. A second sketch displayed only one selected link, but its route was still occluded by adjacent surfaces; the user could read the source and target names without being able to trace the connection visually. Both riser and selection controls were removed from the active study, returning `?mode=three` to surface rails. Their earlier generated captures are not current evidence. **Overlapping and hidden links remain unresolved.** A future comparison should test a route corridor along visible container edges or a restrained inspected-link overlay against the same fixture before adding another endpoint treatment. These options are proposals, not implemented results.

## Relationship inspection instead of another connector shape

After the user found the restored rails unsatisfying too, the study added a complementary relationship inspector. At `?mode=three&inspect=app`, the right panel lists all incoming and outgoing links for App Service by source, target, and endpoint semantic; the 3D scene emphasizes the block and its directly connected neighbors while retaining the surface rails. The default `?mode=three` lists all five links. Reproducible captures are generated in `iterations/three-relationships/app-service.png` and `iterations/three/rest.png`. A labeled select also works with keyboard input. This matches the production pattern of inspecting selected connections but **does not replace** the active surface-connection design. The candidate avoids adding more geometry on top of overlapping blocks; however, occluded on-canvas rails are still not traceable by sight, and 3D picking, full keyboard traversal, collision avoidance, and production inspector integration remain unverified. The user regards this as the **best available experiment so far**, not an accepted solution, and wants the workflow retained for later improvement.

### Next bounded question

Can a user trace a selected root-to-subnet and cross-subnet connection **on the scene itself** without adding overlapping geometry or relying on the relationship list alone? Compare a visible edge corridor with a restrained on-demand inspection aid using the same model. Mark any occluded segment or ambiguous direction as a failure; include a denser fixture before concluding the approach scales. See [README.md](README.md) for the repeatable experiment procedure and pass/fail/unknown rubric.

### Inspected-link overlay study

The first bounded candidate adds an **optional screen-space inspection path** only when a relationship is selected in the list; all base surface rails remain and the common fixture is unchanged. Same-subnet (`gateway-app`), root-to-subnet (`front-gateway`), and cross-subnet (`app-sql`) captures remain visible above stacked surfaces with a directional arrow and HTTP/DATA label. The user responded positively after seeing this candidate; treat it as the **preferred connection-inspection experiment so far**, not approval to replace the production renderer. See [the dated experiment record](iterations/2026-09-23-inspected-link-overlay.md) for paths and separate pass/fail/unknown gates. This passes the narrow three-link visual traceability check, **not** dense-graph readability, dynamic editing, or real 3D route attachment. The next iteration should hold this candidate against a separately validated dense fixture and smaller viewport, rather than concluding from the five-link image.

### Dense and narrow follow-up — failed readability gate

The separate `?fixture=dense` model has 10 resources and 13 connections; validation passes without changing the five-link baseline. At 1440 × 900 and 820 × 900, the optional selected App Service → SQL path stays visible. However, multiple resource labels overlap in both captures; at 820px the relationship list falls below the scene and is not visible alongside the selected path. This **fails the combined readability hypothesis**, despite the selected route itself remaining unobstructed. Keep the dense fixture as a reproducible stress case, not as an approved visual layout. See [the dated evidence record](iterations/2026-09-23-dense-responsive-inspection.md) and regenerate `iterations/dense-responsive/{desktop,narrow}-app-sql.png` with the capture command. Next question: can the selected relationship and scene share a narrow viewport without masking dense labels? Do not infer production editing or accessibility from this screenshot test.

### Internet and zoom extension — navigation, not readability

Following the dense comparison, the user requested zoom and noticed Internet was missing. The current fixture models Internet as a root external block connected to Front Door by validated HTTP; both baseline and dense variants inherit it. The study has 60%–180% zoom, reset, and drag-to-pan in Lit 3D. The actual editor baseline also displays Internet. The user approved this navigation study as a useful direction, **not** as production renderer approval. This changes the fixture after the earlier historical captures: **current counts are 7 resources/6 links and 11 resources/14 links**, respectively. Zoom out gives a whole-scene view but makes dense labels collide; zoom in requires panning to see outside the viewport. See [the dated navigation experiment](iterations/2026-09-23-internet-and-zoom.md). Do not interpret this as a solution for dense label readability, small-screen inspection, or production editing behavior.

### Resource movement — in-parent drag only

The user asked whether resources could be moved rather than only panning the scene. The isolated Lit 3D study now distinguishes starting a drag on a resource from empty-space camera pan. A snapped, same-parent move is checked against canonical placement, parent bounds and sibling overlap before it changes transient study state. Accepted moves recalculate resource geometry and linked surface/inspection paths; rejected overlapping drops restore the original block and path. Zoomed/panned behavior was captured and checked too. See [the dated movement experiment](iterations/2026-09-23-resource-move.md). **This is not production editing parity:** the first movement snapshot preceded the PaaS fixture correction and used App Service as if subnet-hosted. That historical capture is not current evidence. The original fixture definitions still reset on reload.

### Parent transfer, live preview and history extension

After the user requested the omitted interactions, a second bounded movement experiment added transient parent-aware positions to the Lit 3D study. Valid App Gateway transfers from App Subnet to Data Subnet select a free destination slot; a live inspection path and the directly affected rails preview the move while the pointer is down. Rejected root placement for SQL and sibling overlap preserve history and links. Arrow keys and visible nudge buttons move a selected resource one grid unit, and Undo/Redo buttons plus standard shortcuts restore transferred positions. See [the dated extension](iterations/2026-09-23-transfer-preview-history.md). This supersedes the earlier study's "same-parent only" limitations, **not** its warning against production parity: fixture models remain immutable, product store/history are not used, and generalized reflow, dense layouts, assistive review and persistence are not verified. App Service/Functions stay at root; their HTTP/DATA edges do not assert VNet Integration semantics.

### Azure locality audit — corrected service placement, unresolved networking model

The user noted that App Service and Functions do not live on subnet surfaces. A full [resource-by-resource audit](iterations/2026-09-24-azure-locality-audit.md) also identified SQL Database, Key Vault and Cache as managed PaaS outside the VNet. The current study fixtures place all of these at root; only Application Gateway remains on App Subnet. SQL/cache root placement is now allowed by the shared schema while retaining older subnet placement for workspace compatibility. A private endpoint is representable as a subnet block, but its target service and VNet Integration are **not** first-class relations, so neither has been fabricated in this study. HTTP/DATA arrows are logical flows, not proof of private network topology. Application Gateway moved to Data Subnet is strictly a UI transfer test; real Azure gateways require a dedicated subnet. Provider fidelity and export semantics are blocking product-model questions, not claims this renderer spike can settle.

## What is not decided

- The original reference image and crop set have not been added; attribution and reuse rights are not known. See `ref/README.md`.
- The image's independent Region + VNet stack is not representable by the current schema. The valid fixture uses root VNet, two subnets, resources, and a display-only ground.
- The same scripts have **not** dragged, rejected, linked, selected or zoomed objects across engines. The candidate button strips demonstrate a rendering direction only. Functional parity, keyboard/screen-reader navigation, reduced-motion alternatives and low-end performance all remain **unknown**, not pass.
- Labels in the 3D candidate are intentionally overlaid; port glyphs target rx=12, ry=6, height=5 screen pixels, but zoom and depth behavior are unverified. No production port standard change is proposed.
- The original 3D screen-space L-shaped link overlay floated across the scene. A local follow-up replaced it with typed, axis-aligned 3D rails on display surfaces, routing root-to-subnet along the left entry and cross-subnet links through the short gap. This is **not** a reuse or validation of production `surfaceRouting.ts`; routing around arbitrary blocks and dynamic container sizes remains untested.
- The production baseline scene is larger than the candidates in their chrome. Align the inner scene framing before a human visual score.

For the five-link fixture specifically, **relationship inspection passes** the narrow check of listing source, target, direction, and type for App Service (unit tests and `capture.spec.ts`). **On-scene link traceability fails** for Lit 3D where stacked surfaces hide route segments, even with a single connection selected. Neither result implies real-editor interaction parity or performance readiness.

The user's Lit 3D visual preference does not score every aspect of hierarchy, material, and labels against the reference. The next gate is one same-fixture, real-action vertical slice: placement into an allowed subnet, rejection at an invalid parent, a validated typed connection, selection and zoom/pan, with the same actions recorded in production SVG. Include keyboard/reduced-motion behavior, WebGL loss, and measured loaded bytes/frame time. Timebox the slice to one session and record incomplete checks as unknown. Do not supersede ADR-0010 or migrate the production renderer from screenshots alone.
